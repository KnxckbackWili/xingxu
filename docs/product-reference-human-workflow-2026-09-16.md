# 补充参考：让使用者清楚下一步，也放心中途离开

研究日期：2026-09-16。延续[上一轮产品参考](product-reference-study-2026-09-16.md)。以下“官方机制”来自核实过的官方资料，“应用建议”是面向本系统的设计判断；未开展新的用户测试，也未修改应用或部署。

## GOV.UK Design System：把复杂流程说明白

GOV.UK 的价值在于任务状态、复核、完成反馈与错误恢复的组织方式。这里借用交互机制，不照搬它的政务语言或黑白视觉风格。

### 1. 回来以后知道从哪里继续

**官方机制：** 面向需要分多次完成的长流程，入口及再次访问时展示相关任务与状态；任务名称宜用动作词。先精简步骤，再考虑任务总览；状态种类保持少量，突出仍需处理的事项。[Complete multiple tasks](https://design-system.service.gov.uk/patterns/complete-multiple-tasks/)

**应用建议：** 在现有开工准备上增加清楚的“继续办理”摘要，例如“补充服务器信息 · 等客户回复”“确认进场名单 · 待你处理”。下一步旁边写责任人和阻塞原因。已完成事项仍可查看，但降低视觉权重。准备清单、已保存草稿和实际完成必须分别表达，不能以“填过”代替“已准备好”。

### 2. 确认前看清楚，改一处不用重走流程

**官方机制：** 提交前集中复核相关答案，每组信息提供修改入口；修改页保留原填写内容，完成修改后直接回到复核页。[Check answers](https://design-system.service.gov.uk/patterns/check-answers/)

**应用建议：** 在进场确认、移交申请和批量排程等重要动作前，统一使用紧凑摘要：此次影响什么、涉及谁、日期是什么、还有哪些遗漏。现有强制进场确认继续保留遗漏及理由；从摘要修正一个遗漏后返回原确认位置，已填理由不应丢失。普通字段保存无需额外加入确认步骤。

### 3. 提交后明确“办到哪一步，接下来找谁”

**官方机制：** 完成页说明发生了什么、接下来何时发生什么，并提供后续入口及保存记录的方法；用户再次打开确认链接时也应得到有用的信息。[Confirmation pages](https://design-system.service.gov.uk/patterns/confirmation-pages/)

**应用建议：** 扩展已有审批跟踪，把结果摘要放在操作原处。例如“移交申请已提交 · 等待总监或管理员处理 · 查看申请”，避免用户只看到一闪而过的成功提示。明确区分“申请已提交”与“移交已完成”。维修安排成功后显示人员、日期及打开该安排的入口；重要结果可以再次查到。

### 4. 出错时帮人修好，保住已经做的工作

**官方机制：** 校验失败保留输入，在页面上方汇总错误，链接到对应字段；字段旁提示与摘要保持一致。信息要说明具体问题与修复方法，避免含糊代码或责怪用户的语言。[Validation](https://design-system.service.gov.uk/patterns/validation/)、[Error summary](https://design-system.service.gov.uk/components/error-summary/)、[Error message](https://design-system.service.gov.uk/components/error-message/)

**应用建议：** 提交失败后留在原表单，保留说明、日期和人员，直接定位需处理项。把“参数错误”写成“请填写强制确认理由，说明未完成准备项的处理安排”；并发修改则说明记录已更新并保留用户草稿以便核对。现有离线队列及保存提示继续沿用，统一各页面“已保存本机 / 尚未同步 / 已提交”的含义。

### 落地时怎么验证

这些是待验证方向，不是已完成结果。下一轮可用四个短场景检查：离开再返回能否接着做；只修改一项是否保留其他内容；提交后能否说清当前状态和下一位处理人；失败后能否找到原因且无需重填。项目准备与日常维修分别检查，避免把所有工作都变成长向导。

## Fieldwire：关联资料打开后，用户仍知道自己在哪里

**已核实的机制：**任务、表单和照片可以在当前页面上打开；在关联条目间有统一的返回控件，关闭后回到原页面。同一时间只展示一个详情层，避免弹窗层层堆叠。任务还可以带检查清单、带时间的讨论、照片和图纸位置。来源：[关联内容导航](https://help.fieldwire.com/hc/en-us/articles/48437890491409-Navigation-Between-Tasks-Forms-and-Photos)、[任务介绍](https://help.fieldwire.com/hc/en-us/articles/360003458332-Introduction-to-Tasks)。

**面向本系统的建议：**

- 从维修任务打开照片、检查要求或车辆履历，查看完返回同一工作位置，保留筛选和未提交内容。手机使用适合小屏的完整详情，避免层叠抽屉。
- 需要说明现场位置时，可以把问题关联到区域或一张现场布置图。先解决“在哪台车、哪个工位”，图纸标注属于后续可选增强，不宜立刻引入完整施工图系统。
- 统一返回、关闭和保存的位置与含义；有修改尚未保存时清楚说明，避免误关后重新填写。

这些属于查看方式与操作连续性的改进，不需要新增一排“照片管理”“关联管理”主菜单。

## 对现有系统的补充判断

以下为代码检查与设计建议，未进行本轮生产写入操作：

- **交接内容需要更具体。**现有 [现场交接页](../frontend/src/pages/pm/project/SiteHandoverPage.tsx)集中保存甲方联系人和入厂信息；[移交申请](../frontend/src/pages/pm/GovernancePage.tsx)另有交接说明与待办文本。建议在移交时自动带出未完任务、未解决故障、待验收文件和现有联系人，让交出人补充重点、接收人直接继续工作。已有数据只引用一次；缺少的客户承诺不能由系统编造，也不需要因此增加一串审批环节。
- **中断后可以继续。**[今日工作](../frontend/src/pages/worker/TodayPage.tsx)已经有离线队列和本地保存提示。应检查并统一其他长表单的草稿与失败重试体验；接电话、切页面或网络短暂中断后，不应要求从头再填。草稿与正式提交分开表示。
- **等待也有明确去处。**首页可区分“轮到我处理”“等别人回复”“即将到期”。例如等客户提供停机窗口，应显示正在等谁、何时再跟进；仍保留到期事实，不把等待理由自动当作免除责任。
- **用现有记录生成摘要。**交接和阶段报告可以从任务、故障、日程、交付状态生成可核对的草稿，人只补充判断和缺失信息。生成的数字、照片和结论都有原记录可查，不把填写另一份报告变成额外负担。
- **更容易找回刚才的工作。**最近访问、常用项目、按车号或工作名称搜索，以及返回后保留日期和列表位置，适合解决“我记得看过，却不知道在哪里”。这些是直接查找工具，不需要恢复前端 AI 助手。

## 与上一轮建议一起安排优先级

1. **优先完成：**统一工作详情、保持返回位置、明确保存与提交结果、压缩手机导航。这些直接减少每次使用的阻力。
2. **随后完善：**模板到实施计划的连续操作、检查关联未解决事项、自动整理交接清单。
3. **按实际现场需要增加：**现场布置图定位、更多离线资料、阶段报告自动草稿。先复用现有数据，不通过增加主页面来承载每个小能力。

验收时让首次使用的人完成“被打断后继续填报”“查看照片后回到原工作”“接手别人项目找出明天要做的事”三个场景，观察是否需要解释菜单位置、重复录入或重新找资料。这些是后续验证目标，本次尚未做用户测试。
