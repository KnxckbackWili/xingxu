## 本次落实的优化

| 范围 | 原行为 | 优化后 |
| --- | --- | --- |
| 总览性能 | 页面并发请求 8 个接口 | 使用一个 `/projects/{id}/overview` 聚合请求；这只表示请求数减少，不等同于响应耗时同比减少 |
| 总览数据 | 聚合接口重复维护任务树、逾期逻辑，已完成日程仍可能进入逾期 | 复用既有任务树和逾期入口，保留阶段、已完成数量、前后阶段关系及解释 |
| 总览查询 | 日程和日志逐条读取用户/任务名称 | 批量读取名称，缺失历史引用时安全显示空值 |
| 现场日期 | 项目逾期按服务器日期判断 | 按项目 IANA 时区的当地日期判断 |
| 项目状态 | 草稿等状态显示后端禁止的跨阶段操作 | 与后端相邻状态流转保持一致 |
| 页面加载 | 总览失败后仍可能展示空值或旧值 | 明确错误与重试入口；切换项目时取消在途请求 |
| 问题分类 | 表单以 `extra.device` 平铺字段提交，后端忽略 | 以 `extra: {device: ...}` 对象提交；切换分类清除旧分类表单字段 |
| 问题上报 | 快速双击可能产生多条记录；附件失败重试会重新创建问题 | 同步提交锁、同一上报复用幂等键，兼容 NAS 普通 HTTP 环境；问题创建成功后只重试剩余附件 |
| 指派 | 清空处理人发送 null，但后端不更新 | 区分字段省略和显式 null；省略保留、null 清空 |
| 并发更新 | 页面不传版本号 | 指派、状态更新、作废携带读取到的版本号，过期编辑由后端拒绝 |
| 导入事务 | 唯一约束可能在 flush 时抛错，越过 commit 外的重试逻辑 | 将 flush、审计、通知与 commit 纳入同一异常处理范围；批量冲突回滚后重试 |
| 问题权限 | 只按系统 PM 角色显示管理操作 | 项目壳根据项目负责人、技术负责人、协管和管理角色传递实际问题管理能力 |
| 问题页面 | 无搜索和状态筛选；终态仍可点作废；详情操作可能覆盖正文 | 添加搜索与状态筛选、隐藏非法作废操作，详情操作区参与页面布局 |
| 首次使用 | 首页“创建项目”只到列表；表单下方错误不易看到 | 直接打开创建表单；提交校验失败自动滚动至首个错误 |
| 测试稳定性 | 两个按“本周/最近 30 天”统计的测试使用固定 8 月数据 | 固定测试参考日期，保留删除过滤与跨项目冲突断言 |

## 仍需在后续迭代验证的事项

1. **全站时间显示协议**：后端多处以无时区 ISO 字符串返回 UTC 时间，前端直接交给 dayjs。手机走查中问题上报时间显示为 UTC 小时，需统一序列化与展示约定，再覆盖历史数据、通知和报表；本次项目“逾期日期”修复不等同于全站时间显示修复。
2. **多步骤创建的恢复体验**：新建项目后逐个写入车型再生成任务，仍不是一个原子操作。后续可提供服务端一次性创建接口或持久化的创建进度，避免中途断网后用户误以为完全失败。
3. **生产集成**：AI 未配置时的降级页面已检查；外部 AI 模型、钉钉通知、真实 PostgreSQL、NAS 网络、备份恢复及部署回滚需在对应环境验证。没有向外部渠道发送测试消息。
4. **附件网络歧义**：剩余附件重试能避免重复建问题和重传已确认成功的文件；若服务器已收文件但客户端未收到响应，附件接口本身仍缺幂等键，不能宣称网络歧义下绝对不重复。

## 第二轮：现场使用与信息可信度

本轮从现场人员手机填报、遇到网络故障后的恢复，以及项目经理阅读报告的角度继续检查。落实到 4 个页面：今日填报、问题关注、我的项目、周/月报。

### 已完成

- **不要让网络故障看起来像没工作**：今日任务、问题和项目加载失败时，显示明确的异常说明及重试入口。今日任务刷新失败时保留已加载任务和填写数量，并注明数据可能不是最新的。
- **保护填写成本**：现场问题上报增加同步提交锁与服务端已支持的 `client_uuid`，失败重试沿用同一个键。提交期间禁用表单和关闭动作；失败保留内容；成功后列表刷新失败独立显示，不再把已成功上报说成失败。
- **减少判断和点击**：只有一个项目时自动选择；没有项目时说明联系项目经理加入。严重程度结合影响举例，标题拒绝纯空格；“暂时收起”明确本页保留内容及刷新丢失的边界。
- **适应手机和辅助阅读**：问题详情宽度不超过屏幕，问题标题和状态允许换行。今日数量操作允许换行，保留 44px 按钮高度，为加减和输入框补充可访问名称，明确填写的是本次新增数量。
- **报告不制造确定感**：切换项目或周期时清除旧报告，中断过期请求，失败可重试；无当前报告时禁止打印。没有检出的风险不再直接概括为“整体按计划推进”。项目进度获取失败显示“进度暂不可用”，不伪装成 0%。

### 使用体验判断与后续重点

这些判断基于代码和本地演示环境，尚未经过真实现场人员访谈。当前最值得继续深化的是：项目创建中途失败的恢复（项目、车辆、任务是多步写入）；跨页面的草稿恢复；提醒按阶段和责任人分层，避免所有未完成事项都显得紧急；统一服务器时间与现场时区。它们尚未在本轮完成，尤其不能把仅在本页保留表单称为持久草稿。
