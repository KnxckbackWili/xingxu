# 项目生命周期第五轮复核

> 历史 QA 记录：接口、测试名和结果按当时源码保留，不作为 3.0.0 当前操作说明。原测试现按功能归入 `test_project_lifecycle_boundaries.py` 与 `test_legacy_schedule_preservation.py`；旧行为的保留、迁移或退役见[测试整理记录](test-organization-plan.md)。历史通过数量不代表新功能已复验或已部署。

## 范围与方法

按“创建 → 准备 → 进场 → 任务计划/排程 → 验收 → 完成/归档”的顺序，复核暂停恢复、项目移交、准备需求变化、AI 排程建议及取消安排后的再次排程。先增加隔离数据库回归复现，再修复明确断点。没有接触生产数据、上传、提交或部署。

已检查的业务约束沿用第三轮报告及《项目成员权限》：项目不可见返回 404，额外成员能力不改变归档保护；数量完成不代替安全/必需检查；移除成员前必须交接未完成的已下达工作。

## 已修复

### 1. 排程建议必须能够明确匹配任务和执行人

原 AI 建议接口把全系统用户按姓名组成字典：外项目人员可被指派，同名人员、同名任务会静默选取其中一个。现在只允许唯一匹配当前项目启用人员；任务名称歧义明确拒绝，未知任务维持原返回提示。

建议仅改尚未下达、未锁定、没有填报且未结束/取消的草稿。既有已下达计划与实际发生记录保持完整；自动建议不再绕过普通排程保护。需要下达时复用现有全项目下达流程，保留其范围、版本及成员通知，没有新增分批下达政策。

建议和下达会更新被改变条目的版本，旧编辑页面不能撤销更新后的下达状态。显式传入空执行人可以恢复待分配；月份接口对超出公历范围的年份返回输入校验错误，不再抛服务器异常。

### 2. 已完成项目及并发状态变更

生成、重排、下达、AI 应用与原先的单条日程调整保持一致：已完成项目须先恢复到验收中才能调整日程。已归档保持只读。

排程操作统一先锁定并重新读取项目，再读取/变更日程，锁后重验可见性、能力与项目状态。状态切换也在项目锁后重验。与现场报工统一为项目优先的锁顺序，避免 PostgreSQL 上“报工持有项目锁等待日程，排程持有日程锁等待项目”的反向等待。

若等待期间重新排程删掉了旧草稿，编辑请求明确返回 409，要求刷新，不能变成 500。显式状态切换会同时更新项目版本；已加载旧活动状态的资料编辑和团队模板操作，不能在等待归档后继续写入。

这部分已做 SQLite 隔离回归和交错操作模拟；没有声称在真实 PostgreSQL 环境通过并发验证。

### 3. 取消/结束历史与仍需执行的数量

原来未锁定、未下达的“已结束/已取消”行会在重排中被删除；被锁定的取消行又会按旧计划数量占住任务剩余量，并用已取消日期推迟新计划。

现在保留结束/取消历史。取消行只消耗真实已填报数量，不消耗未执行的旧计划量，也不决定新工作开始日期。计划曲线与月历聚合不再把取消的计划数量重复累计，实际填报仍保留。生命周期评估不再把仅剩取消状态的确认行当作有效下达依据。

### 4. 准备清单引用、日期和评审

新增/编辑影响任务或阶段时校验归属；历史错误引用不会解析出其他项目名称。可以明确清空影响关联。更新名称、风险、责任方时沿用新增的字段校验。

准备完成日期、逾期判断使用项目现场时区。准备评审快照补齐旧要求日期、承诺日期及实际日期，因此已打开的旧评审不能确认后来变化的旧日期字段。新增预计延期、收紧要求日期时，原带风险进场确认需要重新核对。同名风险事项按各自 ID 保留，不再因名称相同漏掉其中一个。

没有改变正常进场与有风险进场的必需/可选门禁政策。

### 5. 治理移交也须完成工作交接

普通成员移除已经有交接检查，但原移交审批直接移除旧负责人，可能留下他仍被指派却已失去项目访问的已下达工作。

现在移交与成员移除复用同一检查规则：有未完成已下达工作时，审批保持待处理，负责人和日程都不部分修改；先改派/取消安排再批准即可完成移交。已有质量检查政策、历史报工归属和移交后权限回收不变。

### 6. 验收与归档的附件证据

验收记录、归档清单关联附件前，均确认附件存在且属于当前项目，不能挂到其他项目的文件。清除原附件的现有操作继续可用。

## 保留的产品决策

- 自动 80%/90%/95% 阶段推进没有调整
- 验收完成门禁采用“已有通过记录”还是“最新有效轮次”仍保持现行逻辑
- 单件任务标准耗时 24 小时会拆成三天，当前每日数量为 1/0/0；这些零数量日期也可能用于表达占用工期。本轮保留按件分配口径，没有擅自改为 0.33/0.33/0.34。若希望每日显示可填报的分摊数量，需要先明确按件进度与工期占用的产品语义
- 没有新增采购/制造执行、自动改派、自动接纳进场风险或新的分批发布制度

## 回归验证

新增用例集中在 `backend/tests/test_round5_project_lifecycle.py` 和 `backend/tests/test_round5_scheduler_integrity.py`，覆盖失败原子性、同名歧义、跨项目引用、历史保护、旧页面版本、等待锁期间状态/草稿变化及保留政策。

- 初次复现：19 条隔离用例在修复前失败，首批修复后与原 AI 用例共 21 条通过
- 中间扩展：139 条通过；补齐锁序、取消统计、完整验收归档及治理测试后扩展为 151 条通过
- 最后状态版本/归档竞态修复后：8 个相关文件共 90 条通过
- 最后 AI 无差异草稿发布修正后：11 条相关用例通过，覆盖首次下达与已发布后重试
- 两个新增回归文件共 47 个用例；其中包括保持 1/0/0 拆分现行政策的测试，不能把用例数当作独立缺陷数
- 差异空白检查通过

以上不同测试批次有重叠，不能相加当作全站用例总数。全站完整测试由独立最终验证统一执行；生产构建、浏览器验收和真实 PostgreSQL/Docker 验证应分别说明，不能互相代替。
