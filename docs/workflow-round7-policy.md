# 第七轮：三项已批准生命周期规则

## 范围与结论

本轮落实已确认的三项规则：未满足进场条件必须明确批准风险进场并写理由；完成与归档使用最新有效验收结果；联调、试运行、验收由授权人确认，百分比不代替业务决定。仅修改隔离开发副本，未操作生产；本文记录本地验证，远端提交以交付记录为准。

未扩大为新的审批系统、阶段客观标准或逐车验收模型。既有安全质量门禁、交付 `done` 语义、相邻阶段顺序、人工数量完成权限不变。必需交付必须提交还是必须独立审核，仍是此前另列的待决定政策。

## 1. 当前风险进场决定

- 进场条件 = 未通过/非不适用且 `is_required` 或 `blocks_entry` 的准备项；空清单同样需要明确说明
- 普通可选且不阻塞进场的事项不会被错误升级为硬门禁，仍显示未完成和风险提醒；`ready` 评审可以保留这些普通可选事项
- 任何进入 `executing` 的路径均复核当前条件，包括 `ready→executing`、`commissioning→executing` 及暂停后恢复至 `executing`
- 条件未满足时，必须已有当前有效 `risky` 评审、非空理由和当前事项快照。沿用现有风险评审授权，没有新增安全豁免角色，也没有把用户认可的风险评审偷换成“所有阻塞项绝不可接受”
- `confirm_warnings` 参数保留兼容解析，但省略、`false`、`true` 均不能替代风险批准，缺少有效批准返回 HTTP 400 并指向准备评审
- 旧 `/preparations/confirm-ready` 遇到未满足条件，必须显式 `risk_entry=true`，并在 `conclusion` 写理由；仅普通备注不能自动变成风险批准。新界面使用现有 `/review/confirm` 的显式 `risky` 结论
- 当前状态摘要在锁后刷新子记录。新增/加重条件、同一事项名称或数量规格变更、由非空清单删成空清单、较新的 `not_ready` 决定均不能继续借用旧风险批准。没有事项 ID 的旧风险快照不按同名猜测新事项
- 评审保存原始历史，不把未完成项偷偷改成通过。改善已批准遗留项不会抹掉原风险决定
- 新评审在项目锁内生成单调录入时间，查询以 `reviewed_at DESC,id DESC` 确定顺序，避免同钟刻度下较早决策抢回生效权

API 增补：manifest 的 `entry_unmet` 为数组；summary 的 `entry_unmet` 为数量、`missing` 为布尔值；原 `unmet`/`unfinished` 全量字段保留。`forced_ready` key 保留，中文改为“已批准风险进场”。

## 2. 最新有效验收与范围

### 生效顺序

1. 验收日期 `accepted_at` 为结果的业务日期，日期较新者优先
2. 同日按服务端录入时间 `created_at` 降序；旧 NULL 时间显式排后（SQLite/PG 一致），完全相同时按 ID 降序，结果确定且可复现
3. API 新录入在项目锁内保持单调录入时间；同日更正记录可以取代同日先前结果
4. 回填较早日期的旧记录只补历史，不覆盖较新日期的决定
5. 新记录不允许晚于项目当地今天。旧未来日期记录保留，日期到达前不作为有效结果，并明确显示警告；没有新建“预定验收”功能

选择最新有效记录以后再判断其结论和范围；不能先筛选 `accepted`，不能跳过最新拒绝/有条件通过/范围失效行去找历史通过。完成和归档使用同一检查。当前最新通过结果仍须同时满足原有数量、质量、交付、问题等门禁，签字可提前录入并不等于允许提前完成。

### 最小范围记录

只新增 nullable `acceptance_records.scope_fingerprint VARCHAR(64)`。新签字记录服务端计算的范围哈希；不允许请求体提供该值。范围包括：

- 实施任务身份、名称/要求说明、数量类型和目标、单位、车辆适用类型、安全标记
- 必需/安全检查定义与适用性，不含当前勾选结果或检查人
- 全部项目任务的必需交付定义（也包括准备提醒任务原先就要求的必需文件）
- 车型身份、类型、型号、数量和配置

项目备注、人员、项目状态、排程日期、数量填报、交付/检查执行身份和时间、展示顺序不影响范围。必需交付的要求说明属于定义；提交/审核证据不属于范围哈希。精确恢复原定义可再次匹配原签字范围，不新增不可逆失效历史。缺失/NULL/空字符串的可选文字与数值1/1.0统一规范化，避免普通表单回存误失效；已有交付要求的description在提交/审核时保留，不能因提交证据被重建丢失。

范围变化只使旧签字不再可用于新的完成/归档决定；不删除历史签字，也不自动倒退已经存在的生命周期状态。追加工作即使立即完成，也仍需当前范围的新验收决定。

### 前端单一依据

验收列表/创建响应包含 `is_effective`、`scope_verified`、`scope_current`、`effective_date_reached`、`invalid_reason`。项目详情、overview、handover-summary 都返回同一服务计算的：

`acceptance_summary = {latest, eligible, reason, as_of_date, pending_future_count, warning}`

`latest` 是当前最新已生效记录或 null；`eligible` 仅表示验收证据这一门禁，不代替所有完成条件。页面不自行从列表首行、历史通过或日期重新推断。`as_of_date` 为项目当地日期，用于新验收日期上限。

## 3. 人工阶段与调用链

`executing→commissioning→pilot→acceptance` 以及相邻回退仅由已有状态端点授权决定。保留 `project.update` 与既有总监治理能力，锁后再次验权；不扩大普通成员、AI 或后台任务的阶段权限。

共享 `advance_project_status`/`regress_project_status` 仅保留计划下达关联的 `planning↔ready`。删除 80/90/95% 的执行阶段自动推进和数量撤回自动回退。报工、正负修正、直接完成、重新打开、撤回、两类离线同步都使用这两个共享助手；即使重复调用或百分比跨过多个阈值，人工阶段不变。

调用面复核：

- 日程确认：可以从 planning 到 ready，不越过进场决策
- 报工/调整/同步/人工任务完成：不推进或退回联调、试运行、验收
- 报表调度：读取阶段并生成报告，无阶段写入
- AI/change set：安全字段白名单没有 status；AI agent token 不能冒充人工登录访问状态端点
- 普通项目更新：没有可直接写 status 的请求字段
- 新建项目：仍仅允许四种原有初始状态
- JSON 新建项目导入：预检和执行均拒绝 executing/commissioning/pilot/acceptance/completed/archived/suspended。明确要求先将导入数据改成允许的初始状态再由授权人推进，不静默降级或复制别人的验收权威
- 克隆：原有仅复制计划/清空执行证据的语义不变；完整系统备份恢复与新项目 JSON 导入不同，本轮不改完整恢复流程
- 个人演示数据：保留已有合成示例初始化，不能据此修改真实项目或产生真实验收证据

## 4. 迁移与历史兼容

- Alembic 增量 `a1c7e9b204d6` 接续 `f7b3c8d2a901`；SQLite/PG 启动轻量补列同样增加 nullable 列，无默认哈希、无数据回填
- 历史记录没有可证明的当时范围，因此 NULL 明确表示“范围未验证”。读取不会伪造签字范围，也不会改旧项目状态
- 历史活动项目仅有未验证旧签字时，再次确认完成需要复核当前范围后录入新验收。历史已完成/已归档保持原状态；归档恢复可以先回 completed，再回 acceptance 整改；重新归档必须通过当前门禁
- 发现并先复现一项旧启动缺陷：SQLite `_migrate` 每次将合法 planning 改 preparing、archived 改非法 closed。移除这两条过期转换，重复启动保持合法阶段和归档只读锁。PG 路径原先在该片段前返回，无对应转换
- 对已经存在的未知历史状态不猜测映射、不静默打开写权限；保留只读查询，业务写入提示管理员根据原备份/审计核对修复。不能声称本轮自动修回已经被旧启动代码改坏的真实数据
