# 事件触发资料与问题性质（T24）

`Issue.nature` 独立于硬件/软件等 `issue_type`，取值为 normal（普通）、accident（事故）、quality（质量问题）。项目端和现场端均可选择性质；有问题管理权限的人员可在详情中更改性质，服务端保留既有处理人权限、关闭/作废仅 PM 或报告人、`can_close`、作废理由及状态流转规则。

## 真实来源与截止

每个真实触发保存一条不可由客户端伪造的 `document_trigger_events`。它保存项目、来源类型/ID、真实登记时刻、操作人和来源说明；资料的 `trigger_ref` 指向该事件 ID，`triggered_at` 必须等于持久化事件时刻。实例化会核验事件确实存在、项目及触发类型一致、UTC 时刻一致，不接受任意引用字符串。

| 来源 | 资料 | 时间依据 |
| --- | --- | --- |
| 新事故上报 | 6.6 事故报告 | 真实问题上报时刻 + 项目规则偏移，标准24小时 |
| 新质量问题上报 | 6.8.1 质量反馈单；6.8.2 可选返厂申请 | 同上，标准24小时；6.8.2仍非必需 |
| 普通问题升级为事故/质量问题 | 对应上述资料 | 本次性质变更的真实登记时刻，来源同时保留原上报时刻。界面明确不代表事故实际发生日期 |
| 成员名单移出或移交后实际离开 | 每位离开人员各自的6.7留存资料 | 本次确认移除登记时刻，标准0小时；操作前提示离开前交接 |

规则来自项目定义快照，按平台及实际车辆范围筛选。自建同触发类型规则也通过同一服务生成。组/legacy 不生成实例。幂等键对同一问题及性质唯一，重复离线同步、批导入或性质反复切换不会重新刷新同一义务。再次加入后再离开的成员，以不同项目版本产生独立来源记录。提交历史和文件继续保存，原已提交资料的截止不改。

生成来源、资料、截止、业务变更和审计在调用方同一个项目锁事务内完成。失败全量回滚；并发重放同一来源只生成一套义务。未配置匹配规则或逐车规则尚无车辆时，仍保存真实上报，在资料页显示未匹配警告，不捏造车辆/附件，也不阻止事故上报。

## 成员移除与治理移交

普通成员调整先 GET `/api/projects/{pid}/members/removal-preview?removed_ids=...`，逐人显示姓名、留存要求和交接提示。实际 PUT 项目时增加 `member_removal_confirmations:[ID,...]`；锁后按最终真实差集核对，缺少、重复、多余 ID 均409，增加成员不需要确认。原有已下达工作/安全质量尾项交接守卫保留，确认不能绕过它。

治理移交使用 GET `/api/projects/governance/requests/{rid}/member-removal-preview`。批准 POST 原 `/review` 路径时携带同名确认列表；治理操作仍使用 `system.governance.review`，不额外要求通用成员管理授权。批准在项目锁后重新读取操作人、申请和项目事实，再判断真正离开者。原 PM 即使只通过经理字段持有身份，也属于实际离开；仍任技术负责人、活跃协管或按原规则保留 lead/technician 执行身份者不产生离开资料。

项目人员页、统一人员安排页和治理处理页都实际接入预览及第二步确认；取消或离开页面不会提交确认。成员移出不删除其已提交文件或改写原提交人。资料页按真实来源显示问题标题/成员姓名，问题详情可跳到同一事件的资料。

## 按性质处理时限

问题处理 SLA 与资料提交截止是两条规则。修改 SLA 环境配置不会改写资料模板24小时规则。

```dotenv
ISSUE_SLA_DAYS=3
ISSUE_SLA_NORMAL_HOURS=
ISSUE_SLA_ACCIDENT_HOURS=24
ISSUE_SLA_QUALITY_HOURS=24
REPORT_WEEKLY_TIME=20:00
```

普通小时留空时兼容原天数，默认72小时；事故、质量默认24小时。小时有效范围1–87600，非法值回退默认。SLA 从真实上报或本次性质变更时刻计算经过小时。每分钟扫描活跃项目，解决但待确认的问题仍未闭环；只有关闭/作废停止扫描。持久 `issue_sla_receipts` 按问题、性质、小时配置、接收人去重，重启不会重复发同一条。PM和总监接收；无有效接收人时由有读取权限的管理员兜底，或留下无人接收审计凭据。显式读取禁止有效。

提醒写站内消息及既有选配 outbox，不在请求或测试中直接发外部网络消息。`ISSUE_SLA_TIME` 仅保留旧解析兼容，不再控制每日扫描。三个 Compose 入口已接小时配置，并把硬编码周报09:00改为可配置的项目当地周日晚20:00默认。

## Excel、便携导入和保留

原质量问题反馈单 Excel 的版式、字段、照片及导入导出保留。明确导入该表单会作为本次真实质量上报建立来源与待提交资料；表内旧“提交日期”只作日期元数据，不当成精确事故时刻。导出的 Excel 可由用户作为6.8.1真实附件上传，导入操作本身不会伪造“已提交”。六表交付继续保留完整版本，并增加真实触发引用/时间；问题性质使用独立字段，旧扩展性质另列保全。

项目 JSON 仍用于新项目计划导入。源问题性质、来源ID、原时刻和原来源元数据存入 `Issue.source_metadata`，只读标识为未验证导入历史；当前性质默认普通，不把导入时刻伪装成新事故上报或重新启动SLA。详情显示提示，后续明确的性质变更可建立本次真实来源。源触发记录随资料 JSON 保全为只读来源，不在新项目重建为真实触发。完整加密备份承担原项目事实恢复。

迁移 `g3a24b000001` 暂接 `g3a27b000001`，增加 Issue.nature（旧行 normal）、nullable source_metadata 和两张新表，不读取 live ORM、不改旧 extra/报告时间/文件、不补造历史事故。命名 parent→g24 的 SQLite离线 SQL真实执行、失败回滚、FK恢复、PG在线、双方言编译及完整head schema比较均有精准测试；全历史链仍在线执行。

新持久表及保留边界：

- `document_trigger_events`：project_id→projects CASCADE；actor_id→users SET NULL。source_id为原问题/成员的历史身份引用，故不随单条问题删除而丢失。
- `issue_sla_receipts`：project_id→projects CASCADE；issue_id→issues CASCADE；recipient_id→users SET NULL。

两表已纳入项目保留快照；真实非空记录进入#85加密备份，完整校验后永久删除按FK顺序清除。没有新文件根目录，附件及空白模板仍遵循既有UPLOAD_DIR/manifest/SHA契约。
