# 第六轮：现场人工执行闭环审计

> 历史 QA 记录：接口、测试名和结果按当时源码保留，不作为 3.0.0 当前操作说明。原测试现按功能归入 现场工作、物品流水、文件事务及问题指派功能模块；旧行为的保留、迁移或退役见[测试整理记录](test-organization-plan.md)。历史通过数量不代表新功能已复验或已部署。

## 范围与结论

本轮按真实动作顺序检查「计划与数量 → 下达 → 报工 → 质量确认 → 交付审核 → 问题/车辆处理 → 完成 → 返工/撤回/重试」，并追踪库存、文件证据的旁路。方法包括阅读接口及调用关系、先写失败回归、真实 SQLite 独立会话竞争、权限/项目状态在锁等待期间变化的交错验证。

本轮不是“所有组合都已证明正确”。已覆盖的路径和仍需决策/部署验证的边界分别列出。本轮隔离验证阶段未操作生产；提交、推送与部署状态以最终发布记录为准。没有把 SQLite 验证说成 PostgreSQL 验证。

## 已修复的实际断点

### 1. 撤回后，旧网络请求不能把数量复活

复现：工人上报 2 → 撤回成功 → 旧浏览器/离线队列重新发送原 UUID。原实现已物理删掉报工，去重键随之消失，直报、旧 `reports` 批量和新 `ops` 批量都会重新创建数量。

修复：撤回与报工删除同事务写入现有幂等凭证表，按操作人、项目、任务、原 UUID、工作日期记录撤回凭证。管理修正重试沿用原有不按日期去重的作用域。原 UUID 只确认“已撤回”，不生成新行；新 UUID 可以真实重新填报；他人的撤回、其他用户/任务的操作互不混同。

- 没有新模型或生产迁移
- 当前代码没有凭证定期清理；后续若新增清理策略，不能让这些撤回凭证在可能重放期间过期
- 修复前已经撤回且没有保留 UUID 的历史记录无法可靠补出凭证，本轮没有伪造历史
- `sync.accepted` 是队列操作已确认，不代表本次新增了数量；直接接口返回 `accepted: false`

### 2. 修改计划不能让“已做实际量”大于任务目标

复现：已有 4.004 实际量，PM 把目标改到 4，原实现返回成功。车型从 3 辆减为 1、删除车型、改为任务不适用车型，也会把已报工 2 的任务目标重算到 1 或 0。

修复：普通任务编辑、批量目标编辑和车型重算均用原始累计量验证下限。失败时整个请求回滚，实际报工、车型和其他字段不部分变更。需要改正实际量时先走有审计的数量修正；不能通过改小计划隐去实际工作。

计划与报工采用项目优先锁，锁后重新验证可见性、能力与项目状态；已完成项目调整任务/车型数量需先恢复到验收中。车型备注仍可更新。车型重算改变任务目标时递增任务版本，旧任务表单不能覆盖新范围。普通任务编辑返回真实累计量，并清理聚合缓存。

未擅自改动阶段自动推进/回退政策；该问题由生命周期审计和用户决策负责。

### 3. 普通任务编辑不能冒用提交人、审核人

复现：直接 `PUT task` 可以凭空写 `approved`、虚构附件、指定另一个人 `review_by`，绕过专门交付端点的双人复核。反向问题是仅编辑同名要求的说明/必需性，会把现有提交和审核身份全部覆盖掉。

修复：任务编辑只更改要求（名称、必需性、文件类型、说明），同名要求保留已有证据。携带的执行字段若企图改变保存状态，明确拒绝；提交/退回/审核仍须走原专门端点。新建/明确改名的要求不继承旧审核，删除要求仍是项目管理者明确的计划编辑。

既有交付端点保留：提交人由服务端确定、不能自己审核、附件必须属于本项目、换附件必须重新提交、未改动的已审行保留原审核身份、版本冲突拒绝整次更新。

### 4. “任务没确定量”不能借其他任务完成混过总完成门禁

复现：一个正目标任务已完成，另一个目标为空/零但未明确完成的任务进度是 0%，它却不在 `project_completion_blocker_tasks` 中；交接页还列待办，项目完成门禁却可能放行。

修复：按任务完成事实判断，0% 的待确定任务仍阻断。全检查不适用与明确手工完成保持既有例外；安全关键检查仍不可绕过。

### 5. 问题要指派给真正能打开并处理的人

复现：新增、批量导入、改派都可把问题给项目外工人。通知送达，但被指派人无项目访问权，无法处理。

修复：活跃账户之外，还验证当前项目可见范围及成员/问题管理能力。提供 `GET /projects/{id}/issue-assignees` 作为前端候选事实源，避免再次展示全公司人员。作为普通成员参与项目的 PM/lead 被明确指派后，也能处理自己的问题；仍不能因此改标题或改派他人。

保持原问题状态政策，没有擅自要求独立关闭人或替用户改变历史解决记录。相关既有通知测试补上合法成员前置，保留通知数量、分页、跨用户隔离和已读状态断言。

### 6. 库存既要防超扣，也要防同一动作重扣

复现 A：0.3 米材料先领 0.1，再领 0.2，被拒绝为“当前仅有 0.2 米，不能减少 0.2 米”。修复用十进制计算增减，兼容历史微小浮点误差；余额不为负，也不超过现有数量上限。

复现 B：原接口没有动作 UUID，网络丢响应后重发同一领料，只要余额充足，就会再次扣减。现在流水接收可选 `client_uuid`（8–64 字符），按用户、项目、物品、UUID 写现有凭证，余额、流水、凭证和审计同事务保存。同一动作重试返回原流水和当前余额，不再重复扣库存；同 UUID 的不同内容返回 409；下一真实动作使用新 UUID。

- 领料、收料、移库、盘点都验证重试；有同 UUID 的 SQLite 双会话竞争
- 已成功操作的同 UUID 重试可在项目后来归档后被确认，新动作仍拒绝
- 旧客户端不传 UUID 时保留旧兼容行为，不能宣称它自动具有幂等性；新前端需保留“待确认的原动作”而不是每次点击生成 UUID
- 库存长时间打开的完整编辑表单仍无强制版本令牌，本轮没有宣称已消灭所有旧表单覆盖

库存位置另有实际断点：库存 10 领出 2，原实现会把剩余 8 的地点和保管人改为领取地点/领取人。现在出库目的地与经办人只记流水，剩余库存保留原位置与保管人。单条台账只能表达一个地点，因此部分转移明确拒绝并提示先拆分；整行转移和序列号单件转移保持可用。已有正库存时收进另一已知地点也拒绝混并；同地收料保留原保管人；原库存为 0 的首次入库可填写新地点/保管人。原地点未知且已有库存时，不凭新增部分物品的地点猜测旧库存位置，可在实物确认后编辑台账。

### 7. 证据文件不能先删坏，也不能留下悬空引用

复现：附件删除先移除磁盘文件，再提交数据库/审计；提交失败后数据库还认为文件存在，但无法下载。交付已批准、验收/归档/车辆事件正在引用的附件也可直接删掉。

修复：先验证实时业务引用，要求解除/更换交付、归档或车辆事件附件；已保存验收记录的证据不能直接删除。车辆事件新增/替换附件检查存在且同项目，允许有权操作者明确清空链接，之后再删除文件。

数据库删除、审计与收集箱关系修复先原子提交，成功后才清理不再引用的磁盘文件。清理失败记录运维警告、保留孤儿文件，不伪装业务失败或返回误导的 500。收集箱归档复用的文件保留；对应收集箱项恢复待整理/已整理状态，允许重新归档。其他附件、模板参考和任务参考仍引用的同名存储文件也保留。

### 8. 检查确认不能悄悄改写检查人

复现：把“不通过”撤回为“待检查”不会留下审计；对已通过检查重复发送通过，会替换原检查人和通过时间，但没有相应状态变更审计。

修复：取消不通过记录原原因和操作者；已通过项重复确认不改原检查人/时间（包括完整状态请求带 `is_applicable: true`）。真正从未通过/N/A切换为通过仍记录本次检查人，版本机制不变。

## 已走查的人工作业路径

| 路径 | 核对的关键事实 |
|---|---|
| 报工 → 重试 → 撤回 → 延迟重试 → 新报工 | 数量不复活、不重复；新操作可继续；他人无法撤回 |
| 报工 → 管理修正 → 撤回修正 → 重试 | 有效累计在范围内，原历史不改写，撤回修正不重放 |
| 计划修改与报工/车型变更交错 | 项目优先串行；实际量下限；任务版本；整次失败回滚 |
| 已打开计划表单 → 权限撤销/完成/归档 → 保存 | 锁后重验，拒绝迟到写入 |
| 必需检查/可选检查/安全检查/全 N/A/手工完成 | 继承既有三态、数量与质量门禁，安全检查不被手工覆盖 |
| 提交交付 → 管理审核 → 改说明 → 换证据 | 审核身份保留；不能靠普通编辑制造批准；替换要重新提交 |
| 问题上报 → 指派 → 处理 → 解决/重开 | 处理者可实际进入项目；版本、成员范围和终态保护 |
| 车辆故障 → 处理记录 → 正常/重开 → 多故障并存 | 未关闭故障不能被另一事件清为正常；证据关联不跨项目 |
| 库存初始盘点 → 多次领用 → 同动作重试 → 新动作 | 余额与流水一致，浮点可用量正常，同 UUID 不多扣 |
| 交付/验收引用文件 → 删除/提交故障/共享收集箱文件 | 引用保护、提交失败原文件保留、共享来源可恢复 |

这些路径包含新增测试与第五轮回归重跑；不是全部都由新测试独自覆盖。

## 待明确的人工作业政策

1. **维修多轮返工**：当前一条车辆事件唯一关联一个维修任务。若原维修数量已经报满，重开车辆问题后再安排仍复用原任务，不能再次报相同数量。不能为方便返工把原历史清零或凭空增大完成数。现有安全做法是新增一项独立临时返工工作，备注关联原车辆问题。后续应明确“事件下允许多轮维修任务”或“每次复发新建事件”，再实现稳定关联。
2. **问题处理与关闭权限**：既有状态机允许有管理能力者直接解决/关闭；当前没有强制独立复验人模型。本轮不把产品建议当成已授权的新审批制度。
3. **质量粒度**：检查仍按任务，不能据此证明每台车/每个批次都已逐项检验。要逐车/逐批可追溯需要新的质量记录维度。
4. **日程与实际日期**：现有报工允许实际日期与排程日期不同，用于补报/跨天实际发生；本轮未擅自把两者强制相等。今天视图应区分安排日期与真实发生日期。
5. **实体库存完整编辑的旧表单覆盖、物品/车辆导入的重复意图**：未新增全域版本与所有创建路径幂等契约；已验证的库存流水幂等不等于所有台账 API 已具备该能力。
