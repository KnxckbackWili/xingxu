# 项目流程、Agent 与数据可见性

本文按当前页面、路由和权限实现说明产品边界。历史交接稿和旧页面说明仅作背景。项目整体状态、任务阶段、准备就绪、实际报工和质量通过是不同事实，不能用一个百分比互相替代。

第七轮已落实三项确认规则，见 [生命周期规则](workflow-round7-policy.md) 与 [验证清单](workflow-round7-verification.md)。第六轮完整功能清单、历史观测与其余待决定的业务规则见 [独立业务闭环覆盖矩阵](workflow-round6-coverage.md)。该矩阵明确区分源码核查、API 测试、真实浏览器和未验证范围。

## 项目整体状态与任务阶段

标准状态顺序：

`草稿 → 准备中 → 计划中 → 待进场 → 现场实施 → 系统联调 → 试运行 → 验收中 → 已完成 → 已归档`

- 新项目可从草稿、准备中、计划中、待进场开始；手动正常流转只允许相邻环节
- 生成任务不会隐式改变项目状态。确认下达日程可把计划中推进到待进场，不代表已经实际进场
- 系统联调、试运行、验收由有权限的人显式确认推进；报工、撤回和进度重新计算不会自动推进或退回这些阶段。百分比仅提供进度参考
- 完成需要人工操作并验证进度、任务质量、交付、问题及验收；归档另有必需资料和复盘要求。显示用百分比的四舍五入不替代原始任务完成量与安全检查
- 突发停工必须说明原因；恢复只能回到停工前状态。完成/归档项目不能直接调整日程，须按现有状态恢复路径办理
- 任务阶段由项目采用的模板定义，常见包括项目准备、进场准备、到货检查、单车调试、地图与站点、系统部署、系统联调、试运行、培训验收。不是所有项目都有全部阶段，也不因整体状态改名就完成对应任务

第七轮已取消 80/90/95% 自动阶段推进，并统一最新有效验收与风险进场门禁。逐车质量结果、分批发布范围和跨日整数工程量仍需统一产品口径；第六轮矩阵 D4–D6 的剩余边界继续适用。

## 准备、进场与发布

准备清单跟踪范围资料、采购、车辆、软件和进场条件。默认准备与用户显式带入的采购应区分，采购跟进记录不等于采购审批、下单或收货系统。

- 项目准备提醒与现场执行工作分开；当前执行范围判断由 `services/execution_scope.py` 定义，不根据名称近似猜测
- 准备项的必需、阻塞、风险、状态及要求/承诺/预计/实际日期各有含义。关联任务/阶段和附件须属于当前项目
- 评审保存当时快照。正常确认、填写理由的风险确认、暂不进场是不同结论；后续新增或恶化条件可使原确认失效
- 准备条件未满足或清单为空时，进入现场实施必须已有当前有效的风险进场决定和理由。旧 `confirm_warnings` 参数不能绕过；非必需且不阻塞的普通可选项保留提醒，不升级成硬门禁
- 日程确认是**全项目发布**，不自动限制为当前月份、屏幕筛选或 AI 刚建议的任务；未排入任务只提示。分批下达若需要，应先明确范围和预览合同
- 一件工作需 24 小时时，现有排程可能分成三天 1/0/0。数量与每日工时占用未分离，不能把后两天的 0 当作无需施工或已完成证据

## 现场执行、质量与交付

- 现场填报是本次新增完成量；修正和撤回留痕。手动完成状态不伪造真实报工数量，两者在复盘时应分开看
- 检查结果为通过、不通过、不适用；安全关键项不能靠不适用或数量覆盖。当前检查结果属于任务，并非每台车辆一份检查记录
- 车辆台账和故障履历可以追踪具体车辆，维修可转成执行工作；工作量完成不等于所有车辆故障已复检关闭
- 交付材料有提交、批准、退回等状态。改换已审核证据须重新提交；审核身份与未改动要求应保留。项目完成、交接摘要和界面应使用一致的必需/批准规则
- 验收记录是用户录入验收人、日期、结论和证据，不是系统对客户电子签名身份的认证。完成/归档以最新已生效日期、同日录入顺序确定验收，再核对结论与当前范围；后来拒绝不能被旧通过覆盖。历史缺少范围记录须复核后重新录入，新记录日期不得晚于项目当地今天
- 断网可排队保存数量、检查、交付和问题；重新联网后仍需通过当前权限、版本和项目状态校验。被拒操作不是已成功，需用户核对后重试或移除

## 逾期、历史与报表

逾期应结合项目现场日期、有效日程和实际完成情况判断。取消的未执行计划不代表已完成，历史实绩仍须保留。项目总览区分当前、前序及后续阶段的提醒，后续阶段没有交付不必然表示今天该施工。

## 外部 Agent 的权限合同

### 连接与授权

外部 Agent 使用 `/api/ai/mcp/` 或 `/api/agent/tools`。HTTP 桥接复用 MCP 工具注册与 scope 判断；可用工具以实际返回的目录为准，网页配置说明不是另一套权限来源。

1. token 绑定一个系统账号
2. token 的 scope 先限制可调用的工具
3. 账号仍须能看到目标项目；不可见返回 404
4. 排程预览还必须有相应项目能力；可见而无能力返回 403


### 主要动作

| 动作 | 数据变化 | 额外条件 |
|---|---|---|
| 查询项目、计划、准备、日程、问题、物品等 | 只读 | 相应 read scope + 项目可见 |
| 排程预览 | 模拟并回滚 | 预览 scope + `project.manage_schedule` |

### 角色与项目能力

项目可见性和可操作性分开。继承能力取决于管理员、负责人、技术负责人、协管等关系；成员还能获得明确的本项目能力。旧角色名可能仍出现在历史账号中，但不能据角色标签推断拥有全部管理能力。

- 管理员通常有全部项目能力；个人日程等私有资料仍按所有者保护
- 项目负责人/协管按现有能力集合管理；技术负责人通常可管理任务、日程、问题、物品，但不天然可改核心资料或成员
- 普通成员可阅读项目；填报、检查、交付和上报走成员执行规则
- 明确成员授权只在本项目有效，不能建立成员关系、跨项目继承、授予删除或再授权能力；移除成员后旧授权不能继续有效
- token 的 scope 不能扩大被绑定账号的实际项目权限

完整行为以 `services/permissions.py` 与 [项目成员权限](project-member-permissions.md) 为准，菜单隐藏不是安全边界。


项目 JSON/Excel 是可移植业务数据，JSON 导入创建新项目；ZIP 可带附件用于交接。它们不是完整实例备份，不能保证原用户身份、验收/评审、审计、关联和附件恢复。新项目 JSON 导入只接受草稿、准备中、计划中、待进场；后期状态会在预检与执行时明确拒绝，以免绕过进场/验收门禁。完整系统恢复不受此新项目导入规则替代；其余恢复语义见覆盖矩阵 D8。

留存快照记录原业务身份、验收/准备评审/检查状态等结构化证据，另有文件 manifest；字节仍在 uploads，不嵌入 JSON。清理附件必须保留 manifest 中的文件，旧档案无法补回已经丢失的历史，见 [附件清理 SOP](uploads-cleanup-sop.md)。

完整实例备份在「备份与恢复」管理；SQLite 网页准备恢复与 PostgreSQL 脚本恢复的支持边界不同。查看备份成功不能代替实际恢复后核验数据库、附件、密钥和登录。SQLite 迁移会固定同一数据库连接恢复外键约束并验证，恢复失败的连接不得返回业务连接池。

## 数据边界

| 边界 | 示例 | 可见范围 |
|---|---|---|
| 个人 | 本机未同步草稿、个人消息状态、本人 AI 任务 | 当前账号；离线缓存按账号隔离 |
| 项目共享 | 任务、日程、问题、现场联系人、交付要求、附件、动态 | 项目成员及有治理范围的角色 |
| 组织汇总 | 工作台、人员负载、信息统计 | 按当前账号可见范围聚合；管理员/总监可看其治理范围 |
| 系统管理 | 用户、组织、模板、备份、治理审批 | 对应管理员或审批角色 |

现场联系人是项目共享资料，不是私人通讯录；导出也有独立项目能力。项目不可见返回 404，可见但无操作能力返回 403。前端菜单、角色名和项目状态显示都不能替代后端校验。
