## 范围与判定

本轮只把三项已确认规则落实为可验证合同：

1. 必需条件或阻塞进场条件未满足时，必须明确批准当前风险进场并填写理由；旧 `confirm_warnings` 不能代替风险决策
2. 完成与归档采用当前范围的最新有效验收结果，不再搜索任意历史通过记录
3. 系统联调、试运行、验收由具备现有权限的人显式推进；80/90/95% 或报工次数不再推动或回退这些阶段

“通过”仅指下面列出的实际断言。没有用测试数替代完整业务证明，没有宣称全部角色、数据、时序或页面组合已经穷举。后端修改由实现者负责，本文及独立测试从人的目标、失败恢复和旁路出发交叉核验。

## 具体合同与兼容性

### 当前风险进场

- `is_required` 或 `blocks_entry` 的未完成事项属于进场前提；纯可选且不阻塞事项不被新规则变成硬门禁
- 空准备清单需说明本项目无需准备的原因，不能当作所有条件自然满足
- 正式评审通过现有 `review/confirm` 写入明确 `risky` 结论、非空理由、人员、时间和当时清单；当前未完成要求增加或加重后重新评审
- `review_token` 存在时校验当前清单，过时请求拒绝。服务端仍会在项目锁后读取真实现状，不复用 ORM 中旧子对象
- 遗留 `confirm-ready` 接口有未满足条件时，必须显式 `risk_entry=true` 加非空原因；任意备注不等于风险授权
- `ready→executing`、`commissioning→executing`、停工恢复至 `executing` 都经过相同门禁
- 评审仅确认准备决策，不暗中推进项目阶段；后续明确状态操作才进场

### 最新有效验收与范围

- 排序依次为验收日期倒序、录入时间倒序、ID 倒序。较早日期的补录不覆盖较新日期的决定；同日纠正采用后录入结果
- 新验收日期不能晚于项目当地今天。历史未来日期行保留并说明暂未生效，不能用它覆盖今天的拒绝或补足今天缺失的签字；项目时区决定日期边界
- 新录入在项目锁下保证单调录入时间，避免同一时钟值或时钟回退导致后一次纠正被旧结果覆盖。ID 仅用于历史完全同时间的稳定排序
- 最新 `rejected` 或 `conditionally_accepted` 都阻止完成及归档，即使更早存在通过记录
- 验收快照只比较实施范围、必需质量要求、必需交付定义、车型配置；进度事实、成员、排班、项目说明及人员备注不作为范围变化
- 提醒类“项目准备”不计入实施进度，但其必需交付物本来就属于完成门禁，因此相关定义同样进入范围比对
- 验收仍允许从待进场开始提前录入，未新增“签字时必须已100%”规则。真正完成时仍核对数量、质量、必需交付、未关闭问题及当前验收
- 老记录保留原样，缺范围证据不伪造补齐。旧项目不会在读取、升级或进度变化时自动改状态；但重新完成或再次归档需重新核对当前范围并录入签字
- 旧 `archived→completed→acceptance` 恢复路径保留，不因缺新证据而无法解除旧档案锁定；恢复历史状态不等于免除再次完成/归档门禁

### 人工阶段和权限

- 保留原相邻流转、暂停与原阶段恢复规则，以及现有 `project.update` / 继承治理权限；没有按角色名称另建授权体系
- 撤回、增减修正、直接完成任务、重新打开任务、重复状态评估均不能通过百分比改变联调、试运行、验收阶段
- 日程发布使 `planning→ready`、已无下达日程使 `ready→planning` 的计划状态语义保留，它们不是80/90/95%阶段决策
- 普通项目编辑不支持状态字段；AI变更集字段白名单不包含状态；受支持的聊天/MCP/HTTP Agent工具没有生命周期推进工具
- 有效 Agent Token 可以读取其授权项目、提出允许的变更，但不能作为普通用户状态接口的登录令牌。用户JWT接口代表有权限用户的显式命令，系统不能从HTTP请求证明键盘前是物理真人

## 独立发现并交回的缺陷

### 初版范围指纹漏掉提醒任务的必需交付物

复现：完整实施任务100% → 经API录入通过验收 → 新增“项目准备”阶段任务，配置新的required交付文档并已完成提交 → 再请求完成。

初版实际返回200，项目变为已完成。原因是完成/归档门禁扫描全部任务的必需文档，而范围指纹只扫描计入实施进度的任务。相同业务要求在两个判断里作用域不同。

独立用例 `test_new_required_preparation_document_cannot_reuse_old_signature` 先得到200≠400；日志 `round7-prep-delivery-probe.log`。实现者已将全部任务的必需交付定义纳入范围证据，仍不把准备任务计入实施百分比。修复后还验证新签字能够恢复完成，不能只验证拒绝。

另交叉指出风险评审后删除全部准备项会把“对具体事项的风险批准”误作“空清单批准”；实施版本已加入明确失效检查，独立恢复用例通过。

### 初始化曾直接重写合法阶段

后端实现者在迁移核查中发现 `_migrate` 每次启动都把 `planning` 改为 `preparing`、把合法 `archived` 改为未定义的 `closed`。这会破坏人工阶段并绕开仅识别archived的写保护，已删除该错误转换。

独立侧进一步运行完整 `init_db` 两次，分别验证规划状态不变、归档仍拒绝普通编辑、成员授权仍存在，以及有权限用户仍能解除归档并恢复验收。不是只检查迁移函数的集合断言。已被旧版破坏为未知状态的数据不自动猜测修复，见下方限制。

### 空白定义字段曾导致无实质变化也重新签字

独立规范化复核实际复现：必需交付文档已完成且已签字，任务普通编辑仅把缺失的note保存为空字符串，完成接口却返回400“范围已变化”。缺字段/NULL和空文本不应被当成新的文档要求。

单独探针日志 `round7-canonical-probe.log` 为实际400≠200。回归已纳入独立测试并同时覆盖doc_type；实现已统一空值表达，同时继续把非空要求变化保留为真实范围变化。稳定ID、定义列表排序、JSON键排序避免单纯重排影响指纹，配置中的1与1.0也统一表达。后端另补交付状态更新保留原description，防止正常提交丢失要求文本而意外触发范围变化。

## 显式限制与仍需业务决定

1. **真实UI仍未验证**：第六轮已记录云浏览器拒绝本地地址、本机Chromium Unix socket限制；本轮未绕过环境限制。真实页面渲染、实际用户点击旅程和截图不能声称通过
2. **真实运行环境**：本轮独立测试使用隔离SQLite与Python测试客户端；未运行PostgreSQL真实多事务竞争、Docker/NAS部署、断电恢复、真实通知或外部AI服务
3. **验收录入身份**：记录中的客户姓名是有权限用户录入的业务事实，不是对甲方电子签名身份的认证；签字附件的真实内容本轮未人工鉴定
4. **日期由录入者负责**：新未来日期已按项目当地今天拒绝，旧未来行透明保留；系统仍不能证明客户实际签署日期。补录/纠正的日期会影响结论顺序，页面必须明确显示该规则
5. **定义文本纠错**：任务名、任务说明和必需检查定义属于范围证据；系统无法判断一次文字改动是更正错字还是改变要求，保守要求重新核对。项目内部说明/人员备注明确不触发该门禁
6. **历史范围**：范围证据是当前定义比对，不自动补全历史缺失记录，也不证明真实现场执行过程；历史NULL要求新决定时重新签字是明确兼容性变化
7. **交付审核**：既有完成门禁仍采用done，submitted与approved区别没有在本轮擅自升级为“必须审核通过”；逐车/逐批质量记录、分批下达、工期容量模型等仍见第六轮待定列表
8. **完整恢复和新建导入不同**：新项目JSON不得用后期状态绕过新门禁，错误明确且不偷偷重置；完整备份恢复不受新建导入规则替代。导入附件、原用户/评审身份不等于全部历史可重建
9. **既有未知状态**：已经被旧版初始化写成closed等未知值的历史行仍可读取，但普通业务修改会给出需依据备份/审计修复的错误；不擅自猜它原来是完成还是归档。合法archived的标准恢复路径已验证，未知损坏数据的人工修复不在本轮自动完成范围内
