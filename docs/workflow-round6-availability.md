核查日期：2026-10-01。范围：人员不可用时段/技能接口、人员容量聚合、跨项目冲突服务、自动排程的可用性接入，以及生成/重排预览。先按真实使用路径找矛盾，再加入可执行回归；不是根据现有测试数量判定业务正确。

## 已复现并修复

| 场景 | 修复前实际结果 | 后果与处理 |
|---|---|---|
| 两位 PM 同时编辑同一不可用时段：都读到 10月1–10日，一个把开始改为8日，另一个把结束改为3日 | 两次各自校验成功，数据库最终保存8日–3日 | 该时段再也不能命中任何日期，系统错误认定人员可用。更新前用现有事务行锁读取最新完整记录，再校验合成后的起止日期；冲突编辑拒绝，不写坏区间 |
| 普通人员直接读取同事不可用时段被403拒绝，但再打开人员看板 | `people[].unavailable_period`、`summary.upcoming_unavailability`仍泄露完整原因、备注和审计信息 | 共用按查看者脱敏的序列化器；只有原 `can_view_user` 授权的人能看详情，其他看板消费者仅获得人员和起止日期 |
| 与目标人员无组织/项目关系的技术工程师调用分配检查 | 角色特例绕过详情权限，直接返回请假原因和私人备注 | 分配检查保留可用性提示，个人详情复用同一脱敏器；没有扩大原详情读取权限 |
| 项目已软删除，历史日程保留 | 配置池项目数为0，计划工时仍为8h | 配置池日程查询补上软删除过滤，人数/项目数/工时作用域一致 |
| 周一查看本周人员看板，某人周五同时被两个项目安排 | 周五2条日程计入本周负荷，但冲突人数和红标都为0 | 冲突统计窗口从周一至今天改为周一至周日 |
| PM在个人演示项目练习排程后，安排正式项目 | 演示工作成为正式排班的跨项目冲突 | 单日冲突和批量冲突统一排除个人演示项目，与自动分配跨项目负载和正式容量统计一致 |
| 账号停用后仍留在项目成员清单 | 管理员看板不计入该人，PM看板仍将其计为在职人员和40h容量 | 相关人员映射统一过滤停用账号；未悄悄删除历史成员/历史工作记录 |
| 项目A预览中，该人员在无关B/C项目同一天冲突，但A不在当天排班 | A预览也返回B/C冲突；A无执行人时甚至把空候选转换为全部人员 | 冲突检测增加“必须包含当前项目”条件；空人员列表就是没有人员；无执行人预览不扩成全员冲突查询 |
| A生成或逾期重排延伸到原项目截止日之后，并撞上另一项目工作 | 预览显示延期，但漏掉真正发生在延期日的人员冲突 | 根据本次模拟结果中有效日程的真实日期取检查范围；重排起点保留用户选定日期，不以旧截止日截断 |

这些修复保持已有授权模型。详情脱敏没有改变管理员/PM/本人/组织负责人的原读取权限；预览冲突查询仍限定当前查看者可见的正式项目，不能以冲突检测为由暴露隐藏项目。

## 代码位置

- `backend/app/services/availability.py`：`unavailability_for_viewer(db, viewer, record, user_name='')`；`upcoming_unavailability(..., viewer=...)`；正式项目冲突范围；`detect_cross_project_conflicts(..., required_project_id=...)` 和空候选语义

- `backend/tests/test_workflow_round6_availability.py`：本轮15项业务回归

## 没有被“修正”为新政策的内容

1. 全员不可用时自动排程仍按现有退化策略生成结果并警告；本轮没有把它改成硬性禁止排程
2. 本周默认容量仍为每人40h；没有擅自把项目周末施工规则改造成个人工作日历，也没有按不可用天数重算分母
3. 一件24h任务可能拆为三天1/0/0；本轮没有将零数量日程当作应删除的记录，数量与每日占用工时仍需产品级定义
4. 分配检查仍然是提示，人工可以在提示后安排工作；本轮没有改成冲突即拒绝
5. 跨项目自动分配负载仍限当前查看者可见项目；组织级配置池可以显示匿名总承诺，但不能借此推导或暴露隐藏项目名称
6. 不可用时段是日期范围，当前并无个人时区字段；本轮没有将它自动按不同项目时区换算

## 已验证的正常/边界路径

- 重叠不可用记录允许并存；取消其中一条，另一个覆盖同一天的时段仍生效；两条都取消才恢复可用
- 已取消日程（`skipped`）、软删除项目和个人演示项目不进入正式冲突/负载计算
- 已拒绝详情读取的用户在聚合和分配检查中不能获得相同私人原因/备注
- 日期部分更新使用两个预先读取旧值的独立数据库会话复现；拒绝后一并回滚，不留下非法区间
- 本周稍后的冲突、原截止日之外的冲突都会出现
- 空人员列表不会变成全体人员；必需项目不存在或不可见时不返回冲突
- 生成与逾期重排预览前后日程ID、日期、执行人、数量完全一致，模拟后回滚
- 隐藏项目与本人可见项目同日同人排程，预览仍不泄露隐藏项目

## 尚需明确的业务边界

- **结束项目的遗留未来日程**：当前 `completed` / `archived` 项目的非 `skipped` 日程仍可能进入冲突和计划负载。过去日程可能是真实已发生工作，不能简单全量排除；未来遗留计划是否在结束项目时取消、或仅在容量计算时忽略，需要确定统一政策。本轮没有静默删改这些历史/未来记录
- **时区与公司周容量**：人员可用性/本周汇总采用服务器日历日；项目现场有独立时区。跨时区“同一天”是否视为同一工作日、跨日实际占用如何折算，当前数据模型没有工作时段信息，不应把日期相等当成精确工时重叠证明
- **旧页面的同字段覆盖**：行锁解决服务器内并发读改写造成非法起止区间；接口未新增版本字段，所以隔很久提交的完整合法旧表单仍可能覆盖后来的合法值。若要求所有人员资料编辑都提示“别人已修改”，需要端到端版本合同
- 技能匹配仍是标签与任务/模块名的包含匹配，没有把技能标签当成资质认证或绝对作业许可
