# 资料表单生成 T35

资料页6.2在项目现场时区当前ISO周提供“由系统生成本周生命周期表”，6.9.3选择已有物品申请生成内部联系单Word，9.2继续由物品与真实收发流水生成。生成后直接保存真实附件与资料新版本，原提交、文件和源记录都保留。归档/权限撤销/不适用范围不能写；历史周次不由当前数据回造，仍需上传对应真实原件。

三项使用同一`generated_document_forms.generate`提交事务。服务在项目锁内取来源、创建产物、末次复核账号会话/资料资格/来源范围，然后`create_attachment`、统一独立保密helper、`docs.submit`与审计一起提交；失败回滚附件、版本、状态和新文件。完整SHA-256使用真实生成字节。`DocumentVersion.review_metadata.generated`保留生成时刻、生成者、来源记录ID、原日期依据、当期/时区与SHA，不覆盖生成来源。未新增表或迁移，现有项目快照、备份与版本导出已包含这些事实。

6.2复用`report_forms.lifecycle_to_excel`和公司12列`LIFECYCLE_HEADERS`（见下文“公司表单”），只选择现场周一至周日内原`VehicleLifecycleEvent.event_date`，不使用上传/生成时间替代问题日期。空周只产生原表头，不捏造事件。所有字符串作为Excel文本，避免真实问题标题以等号开头时变成公式。全履历Excel导入导出与质量问题反馈单按公司现行版式。

6.9.3复用原内部联系单字段与顺序，申请日期原样保留，缺失日期保持空白，不把资料提交当成申请审批。Word段后距适度收紧并把签名两行放在一起，标题采用黑色Title样式且清除默认蓝线；普通多行需求可在一页完整阅读。

9.2复用物品与不可变流水表头和字段，时间列为“发生时间（UTC）”。原数量和发生时间不改写。

## 公司表单：生命周期表与质量问题反馈单

两张公司表不是单独的模块，内容来自已有记录：项目信息、车辆和车辆问题。

**AGV生命周期表**（公司现行 12 列）：序号、项目名称、项目合同号、型号、配置号、车辆编号、调车时间记录、车号、分类、变更内容、记录人、记录时间。

- 来源：
  - 项目合同号：项目信息“其他资料”里的“项目合同号”（`projects.contract_no`）。
  - 配置号：车型配置（`vehicles.configuration.config_no`）。
  - 车号：车辆记录。
  - 其余列：车辆问题记录。
- 日期按公司习惯写成“2026.5.23”。
- 同一天、同分类、同内容、同记录人的几台车合成一行：车辆编号用“、”连接，车号用“.”连接，两边顺序一一对应。
- 导入：
  - 只认公司现行 12 列。
  - 一行写几台车就拆成几台车，按车辆编号匹配或建档，每台车记一条已关闭的维修记录（分类、记录时间放在记录的扩展字段里）。
  - 项目合同号、配置号、车号只在原来为空时补上，不覆盖已有值。
  - 同一车辆、日期、内容重复导入时跳过。
  - 表里只有型号，没有车型类别，所以导入不自动建车型。型号还没有对应车型时，车辆页提示“××型号 N 台还没有车型”，点“添加为车型”，选好车型类别即可：型号、台数已经填好，配置号不填就沿用表里的。添加后这些车都挂到这个车型下。把已有车型的型号改成导入的型号，效果也一样。原来的逐车检查都保留，不会补出新的检查。

**产品质量问题反馈单**：版式与公司 A02 版一致。

- 页眉 `HCZN-JY-2026-010  A/02`，A–I 列宽，一页打印；“版本管理”工作表隐藏。
- 车辆的门架号（门架钢印）和出厂日期（铭牌）在车辆记录里填写（`vehicle_units.frame_no`、`factory_date`）。
- 导出入口：
  - 项目问题：问题详情里的“导出单据”。
  - 车辆问题：车辆记录里每条问题的“质量问题反馈单”，以及问题页车辆问题详情里的“导出质量问题反馈单”（`GET /api/projects/{pid}/vehicle-events/{eid}/export/quality-form`，与项目问题的单据导出一样需要“项目导出”权限）。
- 导入只认 A02 版。车辆的门架号、出厂日期为空时，用单据上的值补上。
- 现场照片放进单据上的两个照片框。公司标志不随系统导出。

## 权限与来源

生成目标须通过当前资料家族ACL；独立私密输出复用T26负责人+C_PLAN授权和指定人员校验。默认整行排除私密来源，即使操作者是可读该来源的负责人；缺失、无权限或跨项目原件别名也排除，不披露被排除来源的名称、摘要或数量。

明确选择私密输出时，独立文件的全部指定读者（含当前负责人，以及暂时被目标家族挡住的人）都必须能读来源文件，才可纳入该私密来源。否则仍排除，避免今后家族扩权激活潜在副本。文件限制与目标家族继续取交集，不修改任何原家族范围。

联系单使用既有生成版本的真实申请ID追踪来源约束；旧私密Word缺少可靠申请身份时，不从标题或同名文件猜对应关系，保守约束所有候选申请。公开选择器不显示不适用来源。旧生命周期/Word直接下载入口同样按当前操作者的独立文件与家族交集过滤，并记录实际保密导出审计；它们只向当前操作者下载，不创建更宽的公共资料副本。

## 接口

以下均以`/api/projects/{pid}/documents/{did}`开头。写动作沿用`worker.deliver`，资源可见性、当前ACL及归档边界仍服务端检查。

| 方法 | 路径 | 请求与结果 |
| --- | --- | --- |
| POST | `/generate-lifecycle` | `{note?, confidential?, confidential_user_ids?}`；仅6.2 project weekly且当前现场ISO周；返回完整当前ProjectDocument |
| POST | `/generate-contact` | 同上加必填`application_id`；仅6.9.3 project on_demand；返回ProjectDocument |
| POST | `/generate-inventory` | 旧路径保留，公共字段同上；仅9.2 project lifetime；返回ProjectDocument |
| GET | `/generation-sources` | 可选query `confidential=true&confidential_user_ids=id`（多值重复键）；返回当前输出范围允许的`[{id,title,item_name,apply_date,status}]` |

响应`Cache-Control: private, no-store`。错误范围/归档400、无资格403、不可读或不存在的联系单404、旧周次或生成中权限变化409、会话失效401、非法body422，失败无新提交事实。

## 原件保全补强

元数据盘点确认仅三类旧业务`attachment_id`尚无FK：VehicleLifecycleEvent、ArchiveChecklist、AcceptanceRecord。存储清理现按真实Attachment ID显式保护这三类引用；同名的不同原件不受牵连，不凭跨项目字符串猜测释放原件。保留archive manifest和独立空白资产归属继续保护。预览后新增真实引用导致409，重预览后仅清理无引用旧周次。
