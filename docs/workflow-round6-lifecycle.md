# 第六轮：生命周期、准备、排程旁路及管理信息逻辑审计

## 方法、边界与结论

本轮从人的目标倒推，而不是把路由 200 或测试通过视为业务正确：建项目并明确范围 → 准备评审 → 形成并下达可执行计划 → 现场发生事实与纠错 → 验收 → 完成 → 归档 → 必要时恢复纠错。逐项核对前提、动作、输出、撤回/恢复、旁路入口、旧页面、并发及跨页面口径。

读取了 README、CLAUDE、当前 workflow 文档、第五轮生命周期报告、计划/交接 skill、生命周期/权限/排程/进度/准备/表单/报表/看板源码及对应回归；仓库未发现 AGENTS.md。仅隔离 SQLite 与本地源码，不操作生产，不调用真实通知/AI 服务。本报告不等于真实 PostgreSQL 并发验证，也不代表未提到的所有业务政策已经获得产品确认。

第五轮已有的跨项目附件、日程取消保留、AI 建议歧义与既有下达保护等结论作为基线，不重复计为新缺陷。

## 主要新缺陷与实现说明

### 1. “已完成”之后发生的质量变化曾被归档吞掉

实测顺序：准备一个数量 100%、安全项通过、已录验收的项目 → `POST status completed` 成功 → 检查 API 标记急停复检失败成功 → `POST status archived` 原来仍成功。源码 `progress.py` 的完成合同明确要求质量检查阻断完成/归档，但归档路由只看归档清单与问题。

现在归档重用 `project_completion_blockers`，不创建第二套质量标准；同时与完成门禁共用必需交付物判断，防止“完成后文件被退回、done 已变 false”仍归档。新增门禁不会禁止完成后补文件或复检，只在再次归档时看当前证据。错误包含处理路径，且专门测试修复后能走通，不止测试拒绝。

### 2. 旧会话与串行操作没有统一守卫

准备清单、验收、归档清单、报表导入以及个人日历写入原先依赖最初读取的项目状态。另一些接口已加 Project 锁，因此相同操作从不同页面结果不一致。

写操作统一 Project 首锁、重新读取、能力再验、再读子记录，避免旧权限和旧归档状态继续写。评审还必须刷新缓存的准备项，因为只刷新父 Project 并不能清除 SQLAlchemy identity map 中旧子对象。测试使用两独立 SQLite 会话的交错顺序，不宣称已经复现 PostgreSQL 真并发的所有调度。

### 3. 表单导入把事务切成两半

`lifecycle_from_excel`、`quality_form_from_excel`、`item_application_from_docx` 先 commit，路由随后才 log_change。用审计异常注入可证明接口抛错但车辆/问题/申请已保存。去掉 service 内 commit，路由负责“导入 + 审计 + 唯一最终提交”。失败整体回滚，重试不会因上次半成功而先留下静默业务数据。

### 4. 同一项目的实时数字曾相互冲突

`project_progress_tree` 使用每任务百分比（检查封顶、人工完成、N/A）加权，三个管理视图却用总实际量/总目标。数量刚满、安全仍失败时，项目页 99%，管理页 100%，决策页甚至不再列延期风险。现在统一任务进度加权，原始实际量与目标仍分别返回，不伪造工作量。

按时率另按每一日程实际关联填报核算，不能拿一个任务的总完成量重复覆盖全部日程，也不能把工作日期晚于计划的填报当按时。无日程关联的历史工作不凭空分摊到某天；它仍计入实际工作量。

### 5. 治理申请的并发创建与权限回收

原实现先查询没有同类 pending，再插入申请。通过查询/插入间隙的确定性交错，把第二事务放入，能够实际得到 2 条同类 pending 和重复通知，并非仅靠代码推测。另一独立旧会话在负责人已改变后，也仍能以旧角色创建删除申请。

现在 Project 锁保护当前负责人重验、同类 pending 判断、申请及审批通知写入。治理允许处理归档项目，因此这里不复用“归档业务只读”守卫，不擅自禁止合法的归档项目移交/删除申请。竞争请求需要重试，正常重复被拒绝；低权限成员即使伪造 requested_by/source_manager_id 也不会产生申请或通知。审批、撤回等原业务规则不变。

## 仍需明确的政策与剩余风险

1. **进场决定**：是否任何未满足前提都要求正式带风险评审、理由和风险接收人？当前 warning 确认与 readiness review 是并行入口，省略 `confirm_warnings` 仍兼容旧 API。待用户决定，不能因补了锁就称其已形成强门禁。
2. **联调/试运行/验收阶段**：80/90/95 数量阈值与真实业务里程碑不是同一事实；自动只前进一步的结果取决于评估调用次数。应选择“授权人工确认阶段、百分比仅参考”或另建客观阶段完成条件。当前政策未改。
3. **验收有效轮次**：历史 accepted 记录后新增 rejected 仍满足完成条件。需决定按最新日期/最新录入/显式有效轮次，以及更换范围是否作废旧签字。当前未擅自选择。
4. **交付提交与审核**：交付接口 `submitted` 即 `done=true`，完成门禁看 done，而交接摘要看 approved。选填/字符串是明确实现错误已修；是否必须审核通过才允许完成，需要明确且会影响现有单人项目。
5. **准备提醒与最终交付范围**：准备阶段不计排程和进度，但其交付物是否仍必须在最终完成前提交，需要独立定义，不能简单按“不计进度”自动免除资料义务。
6. **下达范围与重复下达**：当前为全项目；直接 confirm 每次增加下达版本并通知，即便没有新草稿。是否分批、空计划禁止下达、相同内容重发是否需显式按钮，仍是产品决定。
7. **工期、数量、人员容量**：1 件 ×24h 拆 3 天数量 1/0/0，负荷按数量×工时导致首日 24h、后两天 0h；当前未擅自改分摊。数量逾期的 0/0 虚警已单独修复，并不解决容量模型。
8. **组织周容量**：固定 40h 不随休假/项目周末规则变化；同事不可用、整周被排满、阶段并行应当如何影响推荐与自动排程，需要一个明确容量合同。
9. **历史报告语义**：当前报告的项目百分比是当前实时状态；历史期初按当前目标和历史数量计算，不能还原过去的范围/检查/验收快照。需要历史快照时必须新增数据模型，不应把现有汇总包装成历史审计证明。
10. **导入业务后续**：质量表/物品申请重复导入尚无统一请求幂等键；生命周期导入有 import_key。历史车辆故障是否应自动变更当前车辆状态，不能仅凭“历史解决方法”文本推断。导入原子性修复不等于这些领域政策已定。
11. **准备事项改名**：系统知道数量/规格/单位改变是新需求，但“改名是文案纠错还是要求替换”没有显式版本语义；已 passed 事项改名不会自动重新核验。严格进场政策应同时定义实质要求变更与名称纠错。
12. **真实环境验证**：SQLite 顺序交错、HTTP 集成和伪造故障能证明本轮具体缺陷，但 PostgreSQL 多事务隔离、真实通知提供商、生产数据迁移和备份恢复仍需独立环境验证。
