# 保密资料与附件

资料页可以设置保密范围。默认可见人是项目当前负责人（`Project.manager`），另外可指定已经能够查看该项目的启用内部人员。系统管理员、技术负责人、协管、上传人和提交人都不会因这些身份自动取得保密内容。指定名单不会自动授予项目成员资格或全局权限；外部人员永远不能读取保密内容。

资料的设置作用于**此资料要求的全部期次、历史版本和以后生成项**。6.11.6 的 IP、服务器与云服务信息默认保密。负责人变更后，默认权限跟随新的负责人；旧负责人不会因历史身份保留权限。授权修改有版本校验，冲突时需刷新后重新核对。

附件可以增加独立的、更严格的范围。同一个原件被多个资料引用时，读取人必须同时满足所有保密资料范围及附件自身的限制。关闭附件自身的保密开关不会解除其关联资料的限制。版本记录也遵守当前范围，不能从旧版本、未归类文件、其他引用或附件直链绕过。

上传新文件时，负责人可选择“附件额外保密”并指定人员，范围在第一次提交文件的事务内生效。关联保密资料的新文件会自动沿用资料范围，普通成员不能自行设置名单。现有文件通过“附件保密范围”修改，不能用旧上传会话覆盖后来已修改的范围。

账号密码类信息建议保存在密码管理工具中；系统资料中只放位置说明。关闭内部保密开关也不会自动开放外部分享，已有“永不对外”限制继续生效。

授权查看、下载和导出都有审计，包含操作者、对象和操作时间；范围变更保留前后名单和版本。操作记录、通知、门禁拒绝详情同样过滤私密标题。没有权限的人不能从这些提示中取得原文。

项目空白模板和项目复制后的空白原件按资料家族控制。全局尚未填写的模板仍是模板资源，并不因为被项目采用就成为某个项目的业务秘密。普通 JSON、Excel、所选资料 ZIP 和完整项目包仅输出当前授权内容；Agent/MCP 使用同一套权限检查。不能读取的空白原件不会通过克隆或导出转成新的可读副本。

系统备份和永久删除前的项目备份保留完整原文、指定名单及历史版本，继续使用加密私有快照。它们不通过普通业务导出过滤而丢失恢复证据，网页只提供密文，不返回备份口令。持有私有备份口令及恢复权限的运维人员属于恢复信任边界。

旧归档快照保持不可变。含保密内容的完整原文按冻结负责人、冻结指定名单及所有引用范围校验；任何一项不满足就拒绝整份原文。没有保密内容的旧快照继续使用原归档读取权限。旧单文件记录若不能证明归属或范围，仅冻结负责人可核对；没有足够身份记录时需从私有加密备份恢复。列表和校验接口保留安全元数据，校验哈希不会因过滤而被改写。

## 接入约定

业务读取统一调用 `project_documents.can_read_document/file/definition`，项目可见性和动作权限仍由调用入口先检查。外部入口还必须验证自己的分享 scope；这些谓词不会创建外部授权。

范围写入先锁项目、刷新账号及会话版本，再校验当前负责人和 `C_PLAN`，最后执行 CAS。资料实例使用 `version`，要求和附件使用 `access_version`。指定名单是 `confidential_user_ids`；附件的 `confidential_explicit` 区分独立限制与来自资料的派生限制。

分片上传使用无写操作的 `validate_upload_policy(db, project, user, confidential=..., user_ids=...)`；完成新文件时，在首个事务提交前调用 `apply_upload_confidentiality`，再执行原 `submit`。完成会话重试应幂等读取当前文件，不能重新应用旧名单。

内部 `check_transition` 保持无账号、纯读；响应和通知边界使用 `filter_blockers` 或 `redact_document_text`，按实际查看人或接收人过滤标题。不能把内部未过滤结果直接作为接口错误详情。

迁移 `g3a26b000001` 增加明确名单及版本，PostgreSQL 使用 JSONB，SQLite 使用 JSON。旧数据不把管理员、上传者或提交者转换成指定人；历史家族任一侧已保密时，另一侧也收紧，原状态、版本、人员、文件哈希与原件保持。
