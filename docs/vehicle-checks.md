# 按真实车辆检查

按车工作通过 `Task.vehicle_step_key` 明确关联模板或项目已有车辆环节。管理员在模板编辑的数量页选择；项目负责人可在车辆进度表的“检查要求”中关联未绑定工作。系统只按旧 `ProjectVehicleStep.source_task_id` 精确识别历史关联，不按任务名称猜默认五环节。已有检查事实的关联不可改绑。

`VehicleCheckDefinition` 保存项目内不可变的检查定义快照、原检查 ID 和原版本。新工作带入/新实车建档按适用车型生成独立 `CheckItem`，含真实 `vehicle_unit_id`、环节及定义版本；只复制定义，结果一律待检，原操作人、时间、不适用和失败资格不继承。未知车型不能当作免检依据。车型变更只为原先不适用、现在新增适用的真实车辆生成待检；删除车型后类型未知也保守核对。原先始终适用的历史任务级结果不自动扩成一批复核。旧“项目准备”提醒沿既有实施范围规则保留为来源，不重新变成车辆实施义务。

旧检查完整保留任务级 `vehicle_unit_id=NULL`、原状态、原操作人和时间。迁移不为既有车自动增加待检项，不改变 g30 历史完成凭证。旧任务级检查仍约束其精确关联环节，界面明确它不代表逐车核验。负责人可填写理由，选择为既有真实车辆生成复核，幂等添加未生成的待检项，不覆盖原结果。

矩阵批量操作先取得项目共同写锁，再重读检查并一次校验全部单元格。安全关键项必须通过，不能不适用或直接完成覆盖；必需待检项不能覆盖。普通失败只接受负责人当前明确理由、精确检查 ID/版本/失败原因的既有覆盖快照，不能跨车辆使用。检查更新沿用原检查权限、版本和审计，并对逐车检查复用矩阵实施状态集合。停工、只读、无填报权限和非成员不能绕过。

逐车检查读取：`GET /projects/{pid}/vehicle-units/{uid}/checks?step_key=...`。检查状态仍由 `PUT /projects/{pid}/check-items/{cid}` 维护。计划权限明确复核：`POST /projects/{pid}/tasks/{tid}/vehicle-checks/generate`，提交真实车辆 ID 列表和理由。

便携 JSON/克隆只继承检查定义和环节关联，新车辆检查重新待检；原逐车结果、定义来源和版本全部在只读 `execution_evidence` 中保留，不能授予新项目资格。加密系统备份和项目保全快照保留全部原事实；新增检查定义已纳入保全清单。验收范围指纹识别新车辆/检查/关联范围，精确 g30 历史关联和冗余定义快照不会无故作废原 v1 指纹。

迁移 `g3a32b000001` 必须在线执行，离线 SQL 明确拒绝且不输出部分新 DDL。升级前按正常流程做一致备份；不能通过 downgrade 丢弃检查事实。
