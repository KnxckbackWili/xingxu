# 第七轮：已确认生命周期规则的前端对齐

日期：2026-10-02。基线：本地 `7446b0ab3e89b82037acc4c572b8ff3cb8ad9230`，在既有第六轮前端 435 项测试基础上修改。本文记录本地验证，远端提交以交付记录为准；没有部署或连接生产。

## 结论与验证边界

本轮将用户已确认的三个决定接到准备、开工、总览、阶段管理、验收归档和交接界面：

1. 进场条件未满足时，必须在当前清单评审中明确批准风险进场并填写理由。
2. 完成/归档看服务端选出的最新有效验收；旧通过记录不能掩盖更新的不通过。
3. 系统联调、试运行、验收由有权限的人确认推进；百分比只作参考。

**本轮没有真实浏览器 UI 验收：新增真实应用旅程 0、截图 0。** 第六轮已验证的云浏览器 `ERR_BLOCKED_BY_CLIENT` 与本地 Chromium Unix socket `EPERM` 仍是边界；本轮遵照要求未重试、未使用代理或隧道绕过。下面的 Vitest/jsdom 组件、路由意图、模拟 API 和构建证据不能当作真实浏览器、触屏、PWA 离线、打印或生产验收。

## 界面与接口合同

### 1. 准备与开工

- 普通准备确认由评审的 `entry_unmet`（必需或阻塞进场项）与 `missing` 决定。其余 `unmet` 仍可见、仍需跟进，但不擅自把非必需事项升级为进场门禁。
- 有门禁缺项时默认“暂不进场，继续准备”。操作者须主动选择“风险进场，填写理由并明确批准”，理由非空才可点“批准风险进场”。提交保持 `conclusion=risky`、`notes`、`review_token`。
- 就绪评审被服务端判定失效（409）后不能沿用旧 token 再次确认；先重新核对。保留已写理由，但仍须再次明确提交当前评审。
- 取消尚在加载的评审后，再开的新评审不会被较晚到达的旧响应覆盖。重复提交沿用同步锁。
- `entryReady` 被开工步骤和总览共同使用，先排除 `summary.void`；原风险批准失效时移除完成标记并提示重新核对。当前风险批准显示“已批准风险进场，遗留事项继续跟进”。
- 准备页沿用现有 `project.manage_plan` 能力，不因 PM/worker 名称或 `canManage` 后备值覆盖服务端明确的能力列表。

### 2. 总览与阶段推进

- 删除旧“仍然切换”警告确认路线，不再发送 `confirm_warnings=true`。即便收到旧版本 `requires_confirmation` 响应，也只引导到当前准备评审，不提供绕过按钮。
- 进场被拒绝的服务端原因持续显示，并提供“查看进场评审”。完成/归档被拒绝提供“核对验收与归档”。
- `executing → commissioning`、`commissioning → pilot`、`pilot → acceptance` 先显示“确认进入”对话框，再由操作者确认。100% 进度不会发出阶段写请求。
- 总览明确区分当前项目阶段、待完成工作阶段和百分比参考；验收中下一步直接进入验收归档记录区。
- 归档被拒绝时保留复盘文本，阶段失败不会被标记成功。归档、停工及里程碑提交沿用同步锁，取消不会提交。
- 沿用现有 `canManageStatus` / 项目能力授权；共享 worker 有授权可确认，无授权只读。没有增加按角色名直接授权的路径。
- 总览排程口径与既有开工页一致，排除 `skipped` 历史取消安排，避免取消记录使启动清单看似已下达。

### 3. 最新验收与恢复

- 总览、项目详情中的归档页、交接摘要共同读取后端 `acceptance_summary`：`latest`、`eligible`、`reason`，以及 `warning`、`pending_future_count`、`as_of_date`。
- `AcceptanceDecision` 统一呈现最新结论、验收日期、验收人、录入时间及服务端阻断原因。前端不自行排序选取“有效记录”，不把数组第一项当作最新有效验收，也不按“历史存在 accepted”推导完成资格。
- 记录列表用 `is_effective` 标“最新结果”；其他记录保留。`scope_verified=false` / `scope_current=false` 分别提示范围未核验 / 范围已变更，展示服务端恢复要求。
- 明示排序语义：验收日期为结果先后依据，同日按录入时间；补录旧日期不会覆盖较新的验收结果。
- 日期输入以服务端 `as_of_date` 作为项目当地今天，设置最大日期并作表单验证。新签字不允许未来日期；服务端拒绝后错误保留在表单中，已填内容不会丢失。
- 历史未来日期行保留，依据 `effective_date_reached=false` 标“未到验收日期”并展示 `invalid_reason`，不替代服务端当前有效结论；汇总警告在总览/归档/交接中保持可见。
- 归档项目只读，并说明“恢复为已完成 → 恢复验收中 → 纠正/复检 → 重新完成”的路径。已完成后需补报或调整计划时提示恢复到验收中。
- 暂停项目能否录入验收使用 `suspension.status_before`；从准备/计划暂停不会凭空获得验收录入入口。验收录入仍要求 `project.update`，保存验收不会自动改变生命周期。

### 4. 交接摘要

- 同一最新验收摘要出现在交接页面，并在用户主动“带入交接说明”时写入文本。
- 验收决定和服务端警告放在详细工作项前，受限的 900 字交接文本不会先堆满任务后丢失关键不通过结论。
- 待办计数为零只说明“当前工作清单中没有待跟进事项”，仍提醒核对验收和口头约定。

## 回归场景

| 场景 | 证据类型 | 结果记录 |
|---|---|---|
| 未完成必需/阻塞项、空清单缺项、空白风险理由 | 组件模拟 API | 禁止普通 ready；明确选择风险并填写理由 |
| 仅选填项未完成 | 组件模拟 API | 允许普通确认，遗留事项仍可见 |
| 评审 409 → 新清单 → 新 token 再确认 | 组件模拟 API | 保留理由，旧 token 不能重用 |
| 取消加载 → 重开 → 旧响应晚到 | 组件模拟 API | 新评审不被覆盖 |
| 当前风险批准 / 已失效风险批准 | 工具函数 + 开工/总览组件 | 状态、完成标记、下一步一致 |
| 进场 HTTP400 / 旧 requires_confirmation 响应 | 总览组件 | 展示原因及评审路径，无“仍然切换” |
| 三个里程碑 × 100% 进度 | 总览组件 | 仅明确确认后提交；百分比不提交 |
| 取消、重复点击、归档拒绝 | 总览组件 | 无意外/重复写；复盘保留并可去修复 |
| 后来不通过 / 有条件通过 + 旧通过 | 归档组件 | 最新结论显式显示，历史不冒充当前 |
| 范围未核验、复检重新通过 | 归档组件 | 提示补验，保存后刷新当前结果，不自动完成 |
| 项目当地日期上限、服务端日期拒绝 | 归档组件 | 不提交未来日期；失败内容保留 |
| 未来历史行位于列表首位 | 归档组件 | 显式有效记录仍为当前结论，未来行单列警告 |
| 共享 worker 授权/只读、准备/计划暂停 | 组件能力合同 | 保持能力边界，阶段不提供意外写入口 |
| 长交接摘要 | 组件模拟 API | 最新不通过在任务详情前，截断标识及长度保留 |

测试全部使用合成数据与模拟 API；实际后端规则、串行化、迁移及 HTTP 集成证据由后端专项报告负责。测试数不是独立缺陷数，重跑批次不能相加。
