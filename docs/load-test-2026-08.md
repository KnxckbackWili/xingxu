# 100 用户并发压测报告（2026-08）

> 目标：验证「单 Docker 容器 + SQLite」能否满足 100 个账号同时在线。
> 版本：v1.12.0（含 `backend/app/db.py` 连接池调整）。

## 测试环境

- 容器资源：1 CPU / 512 MB（与 `docker-compose.yml` 生产限制一致）
- 镜像：`agv-pm:loadtest`（源码构建）
- 数据库：SQLite + WAL，数据目录挂载到宿主机临时目录
- 测试端：同一宿主机 `httpx` 异步客户端，100 个虚拟用户

## 数据准备

- 创建 100 个 worker 用户，每 10 人加入 1 个项目，共 10 个项目。
- 每个项目配置 2 台车，生成 32 个任务、74 个检查项，生成并确认日程。
- 项目状态推进到 `executing`，每个用户今天有 1 条可填报日程。

## 结果

### 登录（100 次，按 4 波 x 25 并发）

| 指标 | 数值 |
|---|---|
| 总耗时 | 60.75 s |
| P50 | 11.37 s |
| P95 | 18.80 s |
| P99 | 19.05 s |
| 错误 | 0 |

登录是 bcrypt CPU 密集操作，1 核下大量同时登录会比较慢；真实场景登录是分散发生的，不应让 100 人同一秒登录。

### 100 并发混合业务（持续 60 秒）

每用户循环访问：项目列表、项目详情、进度、日程、今日任务、问题，约 20% 请求提交当日进度；同时每 3 秒执行一次 Excel 导出。

| 指标 | 数值 |
|---|---|
| 总请求 | 4841 |
| 吞吐 | 79.2 req/s |
| 200 | 4345 |
| 400 | 496（同一任务重复填报后超过剩余目标，属业务校验） |
| 500 / 超时 | 0 |
| P50 | 1.195 s |
| P90 | 1.794 s |
| P95 | 1.953 s |
| P99 | 2.377 s |
| 最大 | 3.469 s |

Excel 导出（9 次）：P50 3.73 s / P95 4.63 s，全部成功。

## 发现并修复的问题

第一次压测发现 SQLAlchemy 默认连接池（`pool_size=5, max_overflow=10`）不足以覆盖 FastAPI 默认线程池的并发请求，出现：

```text
sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached
```

表现为 41 个 500、49 个客户端超时，吞吐仅 2.75 req/s。

修复：`backend/app/db.py` 将 SQLite 连接池调整为：

```python
pool_size=10,
max_overflow=40,
pool_timeout=10,
```

修复后重新压测，P95 从不可用降到 1.95 s，500/超时为 0。

## 结论

- 当前「单容器 + SQLite WAL」在 100 个用户持续高频率操作下可以工作。
- 真实现场负载通常低于本测试（不是 100 人连续 60 秒循环请求），因此当前架构满足 100 人同时在线的目标。
- 需要保留的边界：避免 100 人同一时刻登录；大批量 Excel 导出和 AI 文件提取应错峰。
